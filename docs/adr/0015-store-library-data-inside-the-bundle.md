# Store a library's own data inside its bundle

Routes, GPX files, notes and file-visibility settings live at `<library>.photoslibrary/karttapallo/`, inside the Photos library bundle they belong to. Derived data — the item snapshot and the converted-image cache — lives in `~/Library/Caches/Karttapallo/`. Machine-scoped settings (`window`, `ors_api_key`) stay in `~/Library/Application Support/Karttapallo/`.

This supersedes the data-layout half of [ADR-0012](0012-track-active-photos-library.md), which namespaced everything under `data/libraries/{hash-of-path}/`. The library-resolution half of ADR-0012 is unchanged.

## The problem the hash could not solve

Hashing the library's path binds its data to _where the library is_ rather than _which library it is_. Move or rename the bundle and every route is silently orphaned: the app reopens, resolves the same library, hashes a different path, finds nothing, and shows an empty map. Copy the library to another Mac and the handmade data stays behind. The `libraries/` directory accumulates one subtree per path a library has ever occupied, with no way to tell live from dead.

The obvious fix is to identify libraries by something more durable than their path. Every candidate was built or tested and every one failed:

| Identifier                 | How it fails                                                                                                                           |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `Z_METADATA.Z_UUID`        | Regenerated by a rebuild, _and_ collides across unrelated libraries — two libraries here share `F051E1C1-…` with zero assets in common |
| NSURL bookmark             | Resolves an impostor as the original when a copy is placed at the original path (`stale=0`, path matches)                              |
| inode / `st_birthtime`     | Both change under `cp -R`; `ditto` and `cp -Rp` preserve birthtime but not inode                                                       |
| xattr marker in the bundle | Survives _every_ copy mode, so a copy is indistinguishable from its source                                                             |

The pattern is that no property distinguishes a library from a copy of itself, because a copy is byte-identical by construction. Identity was the wrong question.

## Containment answers it instead

Data inside a bundle belongs to that bundle. Path, volume, machine and copy count stop mattering, because there is nothing left to look up. A move carries the routes; so does a copy, which is what a copy should do.

This rests on one empirical fact, since Apple documents nothing about the bundle's layout: **Photos preserves a foreign top-level directory across a full rebuild.** Verified by deleting `database/` from a 62 GB library and letting Photos reconstruct from its journals — 4919 assets came back, matching the source exactly, and four planted probe files were byte-identical by SHA-256. Recorded with its numbers in [gotchas.md](../gotchas.md).

The bundle's `private/` directory was considered and rejected: it is an Apple-managed per-client namespace keyed by bundle identifier, with its own conventions and its own cleanup, not a general extension point. Our directory sits at the top level alongside `database` and `originals`.

## Derived data goes the other way

`~/Library/Caches` is excluded from Time Machine by system **path policy**, not by the per-item `com.apple.metadata:com_apple_backup_excludeItem` xattr. The difference is load-bearing: the xattr is per-item and not inherited, so a directory that is deleted and recreated comes back _included_, and `tmutil addexclusion` does not survive that. Path policy is inherited by fresh subdirectories and survives a cache clear. So the ~6.6 GB of regenerable JPEGs stay out of backups with no `tmutil` call anywhere, while the ~11 MB that cannot be regenerated is inside the bundle and backed up.

It is a **single slot**, stamped with an `owner.json` naming the library it was built from; opening a different library empties it. Per-library namespacing was rejected because a wipe costs almost nothing — the snapshot is rebuilt on every startup regardless, and the image cache is lazy (2614 of 4919 assets cached in normal use) and mtime-validated per entry, so it refills as photos are viewed rather than in a bulk pass. Path comparison decides ownership, because a false mismatch buys a rebuild and two libraries cannot occupy one path at once.

A **global** cache shared by all libraries was measured and rejected: the four libraries here share zero asset UUIDs, so there is no deduplication to win, and it would cost the "delete one directory" cleanup story. Sharing `items.json` is worse — it is library-derived, carrying album names, place and description terms and a baked-in "not in album" UUID, so one asset UUID legitimately holds different values in different libraries.

## Albums are keyed by UUID

Album directories are named by album UUID rather than album title, so renaming an album in Photos no longer strands its route, and an album deleted in Photos is recognisable as deleted rather than merely unvisited — which is what lets orphaned subtrees be pruned after a rebuild.

Callers still address albums by name: that is what the item records carry, so it is what reaches the API, and pushing UUIDs onto the wire would move the mapping problem into the client for no gain. Translation happens in `album-store.ts` and nowhere else. One consequence to accept: two albums sharing a title are indistinguishable at the API, so they share one directory (the lower UUID wins, so at least deterministically).

Titles are normalised to NFC on the way in, because Photos stores them decomposed. This is not a corner case — see [gotchas.md](../gotchas.md).

## Consequences

- A read-only library opens and displays normally; a route save returns 500. There is deliberately **no fallback location**, because writing the user's handmade data somewhere that is not the library is the problem this ADR exists to remove.
- Orphan pruning runs after a successful rebuild, guarded on a non-empty roster — an empty roster means the library could not be read, which is indistinguishable from every album having been deleted. Deletion is outright rather than quarantined, because the bundle is inside the Time Machine backup set.
- Album files are served through the API rather than off a static root, since the request path no longer names a directory once directories are UUIDs.
- Migration from the old layout was a one-off script (`scripts/migrate-to-bundle-store.ts`), deliberately not shipped in the app: it reads a layout the app no longer creates.
