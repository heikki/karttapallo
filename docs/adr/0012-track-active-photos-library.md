# Track the active Photos library, auto-detected, not hardcoded or user-picked

The app always operates on the **active** Apple Photos library — the one Photos.app currently has open — resolved at startup from the container bookmark `IPXDefaultLibraryURLBookmark` in `~/Library/Containers/com.apple.Photos/Data/Library/Preferences/com.apple.Photos.plist` (decoded via `URLByResolvingBookmarkData` in the native bridge; reading the container needs the Full Disk Access the app already requires). We replaced the hardcoded `~/Pictures/Photos Library.photoslibrary` default, which silently read the wrong library for anyone whose active library lives elsewhere (e.g. an external SSD).

Two alternatives were rejected. A **user-picked library remembered in settings** was dropped because it adds a picker, a persisted selection, and a read-only mode — all of which exist only to cope with the picked library differing from the active one. **Writing to a non-active library directly** was rejected because AppleScript (`tell application "Photos"`) can only ever address the currently-open library — there is no library-by-path verb and no scriptable way to switch libraries — so location/date writes to any other library would require undocumented direct-SQLite writes that bypass iCloud sync and derivative regeneration. By instead tracking whatever library is already active, reads and AppleScript writes target the same library by construction, so no read-only mode is needed and iCloud safety is preserved.

Consequences: resolution **fails loud, never silently falling back to a different library.** No bookmark readable (FDA not granted) → the Full Disk Access dialog. Bookmark resolves but the path/DB is absent (external drive unmounted) → a blocking dialog naming the volume with Retry / Quit. The literal `~/Pictures` default is used only when no bookmark exists at all. Because UUIDs and album names are not stable across libraries, per-library data is namespaced under `data/libraries/{hash-of-path}/` (cache, item snapshot, album sidecars); `state.json` stays global.

> **Superseded in part by [ADR-0015](0015-store-library-data-inside-the-bundle.md).** The final sentence above no longer holds: hashing the path bound a library's data to where it sat, so moving or renaming the bundle silently orphaned every route. Data the user authored now lives inside the library bundle and derived data in a single owner-stamped cache slot. Everything else here — resolving the active library from the bookmark, and failing loud rather than reading a different one — stands unchanged.
